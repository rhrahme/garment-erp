## Pattern "cannot login" incident + degraded-auth hold fix

- Morning report: pattern (hagan.dp1@gmail.com) could not log in. GoTrue
  actually ACCEPTED their password at 10:33 Riyadh (last_sign_in_at) - the
  bounce happened after login: when Supabase auth is slow, middleware's
  resolveAuthUser timed out, treated them as logged-out, and redirected to
  /login. From the floor this reads as "login does not work".
- Two structural flaws fixed:
  1. resolveAuthUser could not distinguish "no session" from "GoTrue did
     not answer". New resolveAuthUserDetailed returns { user, degraded };
     degraded = timeout / thrown fetch error / retryable status (0, 5xx,
     429). A definitive 401/403 is NOT degraded.
  2. Middleware wall clock was 10s but inner caps sum to 12s (getUser 4s +
     getSession 4s + profile 4s), so the blunt fail-closed path could fire
     before the deliberate handling. Raised to 15s (still under Vercel 25s).
- New behavior: request carries a Supabase auth cookie + degraded auth =>
  hold, do not bounce. Pages get a 503 "Reconnecting to the server" card
  that meta-refreshes every 4s (user stays signed in, page self-heals when
  Supabase recovers); APIs get 503 + Retry-After: 4. The wall-clock
  fallback does the same when a session cookie is present. Users without a
  cookie keep the normal /login redirect.
- Tests: resolve-auth-user.test.ts extended to 6 cases (degraded on dual
  hang, degraded on 0/5xx, NOT degraded on 401, clean resolve). Verified
  locally: cookie-bearing /pattern 200, anonymous /pattern -> /login.
