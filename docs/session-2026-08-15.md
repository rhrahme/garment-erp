# Session 2026-08-15

## Client photo uploads failed for large files (Vercel 4.5 MB body cap) - fixed

- User: "pattern tried to upload images of clients? and it didnt work?".
  Pattern's account (hagan.dp1@gmail.com) had uploaded fine on Aug 13 -
  the role/permission fix from Aug 11 works. What failed is FILE SIZE:
  Vercel serverless caps request bodies at ~4.5 MB, so any phone photo
  bigger than that dies with a platform 413 before
  POST `/api/sales/client-photos` even runs. Our own limits (15 MB
  images / 50 MB videos) were unreachable in production; videos over
  4.5 MB could never work. Evidence: all 92 stored photos came from
  sub-4.5MB request bodies (the two larger stored files only grew during
  server-side HEIC->JPEG conversion). Local dev has no cap, which is why
  earlier curl verifications passed.
- Fix: direct-to-storage uploads.
  - `POST /api/sales/client-photos/upload-url` - validates session
    (`canAccessClientMedia` + `canAccessClient`), media type, and size,
    then returns a Supabase signed upload URL for the
    `erp-client-photos` bucket. Body `{ client_id | replace_photo_id,
    filename, content_type, size_bytes }`. Returns `{ mode: "direct" }`
    on local file storage so dev falls back to legacy multipart.
  - Browser PUTs the file straight to the signed URL (no Vercel cap),
    with the same XHR progress bar.
  - `POST /api/sales/client-photos/register` - verifies the object
    exists in the bucket, re-checks size server-side (deletes the object
    if over), validates the stored filename shape, then attaches via
    `attachSalesClientPhoto` or `replaceSalesClientPhoto` (replace also
    cleans the previous storage object).
  - HEIC now stays HEIC in storage; the existing GET conversion
    (`convertHeicBufferToJpeg`) serves it as JPEG - same as the 87
    legacy `.heic` objects.
- `ClientPhotosPanel` upload + replace both try the signed flow first and
  fall back to the old multipart POST if the API answers
  `mode: "direct"`.
- Middleware: the new nested routes are covered by the existing
  `/api/sales/client-photos` prefix in the restricted-role allowlist.
- Verified locally as pattern (dev server uses the real Supabase
  storage): 5.2 MB JPEG - upload-url 200 signed, storage PUT 200,
  register 201, serve GET 200 with matching bytes; 23.6 MB file
  correctly rejected with the 15 MB error; replace flow keeps the photo
  id, serves the new bytes, and deletes the old object. All test photos
  cleaned from workspace + storage.
