# Session 2026-08-11

## Paste sizes (pull direction) + copy list reliability

### Why
- Pattern operator still could not get sizes onto the L48 Overshirt rows
  (board screenshot re-sent). Two real causes found:
  1. UX direction mismatch: copy is push-only (source -> targets); he stands
     on the row that NEEDS sizes and wants to pull them in ("paste here").
     Target list shows pattern refs, not article numbers, so he could not
     recognize which target was "L48".
  2. Intermittent backend failure: a forced Supabase read that times out
     returns an EMPTY pattern library, so the copy-targets GET replied
     404 "Client pattern not found" / an empty target list at random.
     Reproduced locally: two identical GETs, one 200, one 404.

### Paste sizes button (new)
- `PasteSizesForm` / `PasteSizesModal` (`src/components/pattern/library/`):
  opened from the row that RECEIVES the sizes. Lists this client's filled
  sheets (same garment or shared piece) as sources, radio-pick one, optional
  piece scope, overwrite / fill-empty, one Paste press. Same API as Copy
  sizes with source and target swapped - all write guards apply.
- Buttons added next to Copy sizes on the Pattern order board rows and the
  pattern job page.
- Copy sizes guide popup bumped to v2 (`hagan-copy-sizes-guide-v2-dismissed`)
  so Pattern sees the new Paste flow explained once.

### Degraded-read fix (copy-measurements GET, dashboard + v1)
- GET now reads the warm cache first and only falls back to a forced read
  when the id is missing; if the store is empty (degraded Supabase) it
  returns 503 "Sheets are still loading" instead of a bogus 404.
- `CopySizesForm` / `PasteSizesForm`: one auto-retry on failed loads and a
  load-sequence guard so a stale/failed request can never overwrite a newer
  successful one (React strict-mode double effect exposed this).
