## "Rebuild lines from sales orders" did not rebuild

- The button added earlier posted to `/sync-lines`. `syncInvoiceLinesFromSalesOrder`
  is documented as an **append** operation: it adds articles missing from the
  invoice and explicitly preserves `unit_price` and `quantity` on lines it
  already has, matching by `article_number`. It could not remove the flattened
  lines written by the old merge key, which is exactly what it was recommended
  for. The confirm dialog claimed prices "will be replaced", which was wrong.
- Worse on a combined invoice: `syncInvoiceLinesFromSalesOrders` loops the
  single-order sync per order, and article numbers restart at 1 for every order,
  so order 2's article 1 matched order 1's article 1 and the real line was
  skipped. A 7-order invoice lost lines.
- Added `rebuildInvoiceLinesFromSalesOrders`, which discards `invoice.lines`
  entirely and regenerates from every covered order through
  `buildInvoiceLinesFromSalesOrder` -> `applyAllInvoiceLineReductions` ->
  `renumberInvoiceArticles`, the same path a fresh combined draft uses. New
  routes `/api/customer-invoices/[id]/rebuild-lines` and the v1 twin; both
  refuse an invoice that is paid or carries a payment.
- `rebuild-invoice-lines.test.ts` proves the stale price is gone, that a second
  order's line survives, that two mills stay apart, and - as a regression guard -
  that `sync` really does keep the stale price. 83 tests pass.

## Fourth skill: verify-before-recommending

- The rebuild-lines bug was not a merge-rule failure and not a shipping failure,
  so none of the first three skills would have caught it. The cause was wiring a
  button to `sync-lines` because the NAME sounded right, while that file's first
  doc-comment line said "Append... Preserves entered unit prices".
- `verify-before-recommending` covers: never infer behaviour from a name; check
  what a function preserves, not only what it changes; check how it matches
  records across several orders; make the button label and confirm dialog
  describe the code rather than the intention; never recommend an action that has
  never been executed; and when repairing, assert the OLD broken behaviour in its
  own test so a silent revert is impossible.
  Ship: `8c9d56c8`. Both Vercel Ready (`garment-erp`, `garment-erp-kvsf`).

## Price per meter and meters per piece on the worksheet

- Two columns before Fabric cost, on the screen view and the PDF: **SAR/m** (the
  mill price converted from its own currency) and **Meters/pc** (the cloth behind
  one garment).
- Meters are divided by the piece count because `fabric_cost_sar` on a row is per
  piece. Quoting the whole line's meters next to a per-piece cost would not
  multiply out. The subtitle now states the identity:
  `SAR/m x meters/pc + 5% duty = fabric cost`.
- Verified against the seven Pr Khaled orders: **182 of 182** priced lines
  reconcile to the halala. An earlier version rounded meters to 3 decimals in the
  stored value and 5 lines came out 0.06 SAR off, so the value keeps full
  precision and only the display rounds.
- 190 of 221 fabric lines store `unit_price: 0` and keep the real price in the
  supplier catalog. `cost-hint-worksheet.ts` is imported by a client component so
  it cannot read the catalog; `load-cost-hint-worksheet.ts` resolves the price
  through `getSalesOrderCost` and passes `fabricBasisByLineId` in.
- Both columns join the merge key. A merged row prints one price and one length,
  so two rows that reach the same cost from different cloth (200 x 2m vs
  400 x 1m) no longer collapse into one.
- A missing mill price shows blank, never `SAR 0.00`. Non-length units get no
  price per meter at all.
